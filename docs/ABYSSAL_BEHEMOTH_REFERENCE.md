# The Abyssal Behemoth — reference (v0.13.1)

A very rare, naturally-spawning Nether world boss. Package `com.projecthero.mod.behemoth`; entities in
`com.projecthero.mod.behemoth.entity`; client half in `com.projecthero.mod.client.behemoth`. Config:
`config/projecthero_behemoth.json` (rewritten with any new keys on every start, same convention as
`TitanConfig`). Not part of the Zombie Raid / Supervillain Raid event framework -- like the Titan, it is
its own standalone wilderness (here, Nether) encounter, with its own spawner and its own health-cap
share with `TitanHealthCap`.

## Identity

A "massively enhanced, mutated, ancient Ghast-like creature" (spec), never a re-skinned vanilla Ghast:
a fully custom GeckoLib model (`geo/abyssal_behemoth.geo.json`, 14 bones / 27 cubes -- a lumpy asymmetric
hull, a dome, a front-mounted glowing core, 5 horns, 6 independently-animated tentacles), a fully custom
texture atlas (`textures/entity/abyssal_behemoth.png`) and a 19-clip animation set
(`animations/abyssal_behemoth.animation.json`). Both the geometry and the animations were generated by
`scratchpad/gen_behemoth_model.js` / `scratchpad/gen_behemoth_animation.js` -- GeckoLib's per-face UV
format (`{"uv": {"north": {"uv":[...], "uv_size":[...]}, ...}}`, confirmed against
`software.bernie.geckolib.loading.json.raw.{Cube,UVFaces,FaceUV}`) means the scripts choose and paint
every face rectangle themselves rather than reproducing Mojang's box-UV packing formula. The model is
built at a 4-block reference height (`AbyssalBehemothEntity.MODEL_HEIGHT`); `BehemothRenderer` scales it
up to the entity's real 9-block bounding box (`AbyssalBehemothEntity.SIZE`), the same trick
`TitanFormRenderer` uses for a Titan Shifter's Titan body.

## Movement and AI

`AbyssalBehemothEntity extends Monster implements GeoEntity`, registers **zero vanilla `Goal`s**
(`registerGoals` is empty) -- exactly the "a boss this size cannot afford a vanilla A* search"
discipline `TitanEntity` established for this mod, just applied to a flying creature instead of a
walking one. `createNavigation` returns a `FlyingPathNavigation` purely because `Mob` requires a non-null
one; nothing ever calls it. Movement is a direct AI/physics split:

- `aiStep()` (AI decisions) runs targeting, the phase/enrage tracker, the ability state machine, the
  boss bar and the ambient particle aura -- but never touches velocity directly.
- `travel(Vec3)` (physics) is the *only* place real movement happens: `tickMovementIntent` computes a
  desired hover point (behind/around the target at a phase- and state-dependent altitude, with a slow
  orbiting tangential offset so it never sits dead still), steers toward it with simple critically-damped
  acceleration, and a cheap `level().noCollision` probe biases the result upward rather than into a wall.
  `isNoGravity()` returns `true`; there is no vanilla swim/fly travel logic left in the loop at all.

Targeting (`acquireTarget`) locks onto the nearest valid player within `detectionRange` and keeps it while
alive and within `followRange`, mirroring `TitanEntity.acquireTarget`.

## Combat state machine

One `Stage` (`NONE -> WINDUP -> ACTIVE -> RECOVER`) per `Ability`, plus a shared `globalLockUntil` so two
abilities can never overlap -- the same shape as `TitanEntity`'s own `Attack` enum. `chooseAbility`
(spec section 6/26) builds a *weighted* list from whichever abilities are off cooldown, boosting weights
by context (grounded vs. airborne target, standing directly underneath, group size, own health, how long
the target has stayed airborne for Skyfall) and refuses to immediately repeat `lastAbility` unless it is
the only option. The actual per-ability effect (damage, knockback, particles, sound, projectile spawning)
lives in `BehemothCombat`, never in the entity itself -- the same `AllMightAbilities` (decide) /
`AllMightShockwave` (effect) split this mod already uses for All Might.

| Ability | Method(s) | Notes |
|---|---|---|
| Abyssal Fireball (R-equivalent) | `BehemothCombat.fireFireball` | one `BehemothFireballEntity`, led by the target's velocity |
| Hellfire Barrage | `fireBarrageShot` x `hellfireCount` | per-shot yaw/pitch/speed jitter -- never an identical repeat |
| Magma Rain | `magmaWarning` then (after `magmaRainWarningTicks`) `magmaImpact` | telegraph-before-damage, scheduled through the entity's own per-tick task queue |
| Abyssal Beam | `beamTick` every tick during ACTIVE | sweeps a yaw range over `beamFireTicks`, a thin AABB-based slab check, not a snap-to-player hit-scan |
| Cinder Tether | `fireCinderTether` | only pulls in targets *below* the boss (anti-flight-only mechanic); success opens `lowAltitudeTicks` |
| Netherstorm | `netherstormPulse`, ticked from `aiStep` while `netherstormTicksLeft > 0` | random strikes across a radius around the boss |
| Hellwind | `hellwind` | self-centred radial knockback burst, also reused for the roar on every phase transition |
| Sovereign Descent | `sovereignDescentImpact` once the dive lands | the dive itself is a direct vertical velocity override inside `tickAbility`, not a teleport |
| Skyfall | `fireSkyfallVolley` x `skyfallCount` | homing-lite `BehemothFireballEntity`s (`homing=true`, nudged toward the target every 4 ticks, capped pulses) |

`lowAltitudeTicks` is the one shared "melee window" both Cinder Tether and Sovereign Descent open (spec
sections 11 and 14 both describe the same kind of window under different names) -- while it is positive,
`tickMovementIntent` hovers much lower and closer, and the main GeckoLib controller plays
`ground_idle`/`ground_attack` instead of `fly`.

## Phases and enrage (spec 17-20)

`updatePhaseAndEnrage` reads `getHealth()/getMaxHealth()` every tick: phase 2 (Netherfury) at
`phase2HealthFraction` (60%), phase 3 (Cataclysm) at `phase3HealthFraction` (25%). Each phase transition
plays `phase_transition`, a roar sound, and an immediate `Hellwind` push (the roar itself shoves everyone
back). `cooldownMultiplier`/`speedMultiplier`/`damageMultiplier` (read by `BehemothCombat` and
`tickMovementIntent`) scale with phase and, once `combatTicks` (ticks with a live target, cooling down
rather than resetting when the target is briefly lost) exceeds `enrageTicks` (5 minutes), Abyssal Enrage
stacks its own multiplier on top.

## Damage taken

As of v0.13.3 the Behemoth has no damage resistance at all -- no `ARMOR`/`ARMOR_TOUGHNESS` attributes and
no flat reduction multiplier in `actuallyHurt` (both existed pre-v0.13.3 and were removed after players
found the boss too tanky and the HP bar unresponsive to hits). `actuallyHurt` now just refreshes the boss
bar immediately after applying damage, rather than override the health math. `doHurtTarget` is disabled
(`return false`): there is no vanilla contact-melee -- Ground Attack is the only melee, applied through
`BehemothCombat` like every other ability.

**v0.13.6 fix**: none of that actually explained a real report of "he still doesn't seem to take real
damage" on an existing save. The root cause was orthogonal to combat code entirely -- a `LivingEntity`
loaded from disk restores its *saved* `MAX_HEALTH` attribute from NBT, which is whatever the config said
when it first spawned, not today's config. Every past balance pass that lowered `BehemothConfig`'s health
(30000 -> 3000 -> 1000) therefore did nothing for a Behemoth that already existed in a save: it kept its
old, far higher max forever, so real hits landed but barely dented a bar sized for a much bigger number.
`syncMaxHealthWithConfig()`, called every `aiStep`, reconciles the live `MAX_HEALTH` attribute to the
current config value (rescaling current health proportionally so a hurt boss isn't topped back up) --
this fixes existing saves too, not just new spawns.

**v0.13.7 fix (the actual root cause)**: v0.13.6's fix above was real and necessary, but it wasn't
sufficient -- players kept reporting the boss as "practically unbeatable" even on worlds with a
freshly-spawned Behemoth. `BehemothConfig.load()` deserializes straight onto whatever `Stats` object
already exists in the JSON on disk; every one of those three health-lowering patches only ever changed
the *Java-side default*, and a config file generated back when the default was 30000 kept `"health":
30000.0` in it forever -- `syncMaxHealthWithConfig()` was correctly syncing the entity to the config, but
the config itself was still wrong. Verified directly: a real player config on disk was found holding
`"health": 30000.0`, un-migrated since v0.13.1. Fixed with a `configVersion` field (a boxed, uninitialized
`Integer`, not a primitive with a literal default -- the same trap `TitanShifterConfig`'s own migration
hit and worked around, see its memory notes) that Gson leaves `null` for any file predating it; `load()`
now resets the *whole* config to fresh defaults when `configVersion == null`, then stamps the version, so
every past release's balance intent actually takes effect on old files too, not just new ones. Confirmed
via the client debug harness (see `docs/OATHBREAKER_REFERENCE.md`'s notes on the same tool): a config
file pre-seeded with the stale `30000.0` value, on a clean boot, was correctly reset to `1000.0`, and a
subsequent 10%-max hit landed for exactly 10% -- no resistance, no stale ceiling.

## Texture

v0.13.3 also recolored `textures/entity/abyssal_behemoth.png` (256x121) from a dark red/black lava
palette to a pale, warm-grey vanilla-Ghast palette, with a simple painted face (two eyes and a mouth,
proportioned off vanilla's own `ghast.png`) stamped onto the body bone's front/north UV rect
(`(0,44)`-`(44,70)`) -- "make him look more like a regular ghast." The geometry (horns, tentacles, core)
is untouched; this was a per-pixel HSL recolor plus a hand-placed face, not a re-paint of every face. Done
with hand-rolled PNG decode/encode via Node's `zlib`, same as every other image tweak in this mod (no
Python in this dev environment -- see project memory).

## Boss bar, loot, death

`EventBossBar` (red, no darken-screen) updates every tick, radius `detectionRange * 1.4`, and also
immediately after any hit lands (see `actuallyHurt` above); `die()` clears
it, plays the death roar/particles, calls `BehemothSpawner.onKilled` (starts the post-kill cooldown) and
rolls `data/projecthero/loot_table/entities/abyssal_behemoth.json` (1-2 Abyssal Core, netherite scrap,
ghast tears, blaze rods, a chance at ancient debris) exactly like `TitanEntity.dropLoot`. `xpReward = 500`.
A 3-second collapse (`deathTicks`) plays the `death` animation before actual removal, same shape as the
Titan's own `deathTicks` stagger.

## Natural spawning (`BehemothSpawner`)

Modelled directly on `TitanSpawner`: a slow per-player roll (`spawnCheckIntervalTicks`, default 20s) times
`spawnChance` (tuned for roughly one spawn every few hours of Nether play), Nether-only, never on
Peaceful, 48-128 blocks from the roller, and only if `activeCount` (a bounded `getEntitiesOfClass` scan)
is below `maxActivePerDimension` (1). `findSpot` scans a mid-height band for a genuinely open-air pocket
(Nether has no reliable surface heightmap) rather than a single point check. A cooldown map
(`ResourceKey<Level> -> long gameTime`, primitives only, no leak risk, still cleared by
`ServerStateReset` for consistency) is set both after a natural spawn (`postSpawnCooldownTicks`, 40 min)
and after a kill (`postKillCooldownTicks`, 90 min).

## Health cap

Even the current 1,000 HP (lowered from 3,000 in v0.13.5 after players still found it too tanky) is past
vanilla's 1024 `Attributes.MAX_HEALTH` clamp on some servers' effective health totals once other bonuses
stack, so the shared `TitanHealthCap.NEW_MAX_HEALTH_CEILING` (raised from 2048 to 40000) is left as-is
rather than lowered back down -- it is one shared vanilla attribute, so one ceiling covers every boss in
the mod, and there is no cost to leaving it high.

## Projectile (`BehemothFireballEntity`)

Extends vanilla `Fireball` (what a Ghast's own fireball is) rather than a custom entity from scratch,
purely so it renders through vanilla's own `ThrownItemRenderer` (a spinning, over-scaled, full-bright fire
charge -- `ModEntityRenderers` registers it at scale 4.5) without needing a bespoke projectile model.
Impact always uses `Level.ExplosionInteraction.MOB` (entity damage/knockback/visuals only, no block
breaking) -- the same restraint vanilla's own Ghast fireball uses, so a long fight does not visibly eat
the Nether floor.

## Multiplayer

Everything above is server-authoritative: the combat state machine, targeting, phase/enrage and movement
all run only in `aiStep`/`travel` on the logical server, gated the usual `level().isClientSide()` /
`level() instanceof ServerLevel` way. Animation state reaches every client through GeckoLib's own
networked `triggerAnim` (one-shot attacks) and a synced discrete read in `mainPredicate` (looping states),
the same two-controller convention `TitanFormEntity` already uses. The boss bar, loot and death are all
vanilla server-side systems that already synchronise correctly on their own.
